# 구현과 검사

1. 현재 spec·plan·관련 테스트를 읽는다. 확정된 spec과 필요한 목업 선택, plan이 있는지 확인한다. 없는 단계를 건너뛰어 앱부터 만들지 않는다.
2. 현재 기능 하나를 순차 구현한다. 최초 MVP는 인터뷰와 SPEC-001에서 합의한 기능 한 묶음이다. 새 아이디어는 backlog에 기록하고 현재 범위를 유지한다.
3. plan에서 정한 핵심 검사를 먼저 작성한다. 아직 없는 동작 때문에 실패하는지 실제로 실행해 확인한다. import·구문 오류는 TDD의 의도된 실패로 기록하지 않는다. 유효한 기존 검사는 통과해야 한다.
4. tdd 실습 요청이면 실패한 검사와 기대 동작을 짧게 보여준 후 구현·통과·필요한 정리를 진행한다. 일반 구현에서도 핵심 검사 외 사후에 추가한 검사는 사후 검사라고 표시한다.
5. 관련 검사를 실행하며 구현한다. 기능 완료 시 contract의 빠른 검사 명령(starter는 npm test)으로 누적 검사를 한 번 실행한다. 매 편집마다 전체 브라우저 통합 검사를 반복하지 않는다. 주요 사용자 흐름은 MVP·기존 데이터/출력에 영향이 있는 변경·최종 시점에 실제로 확인한다.
6. 자동 브라우저 도구가 없으면 수강생 수동 확인 항목을 준다. 미실행 검증을 통과로 적지 않는다. 테스트 도구를 설치할 때는 현재 과제의 필요와 환경을 확인한다.
7. .claude/edu-templates/validation.md에 따라 실제 명령·결과·AC·남은 수동 확인을 기록한다. 성공 로그 전체를 문서에 붙이지 않는다. 같은 실패에 두 번 수정 후 해결하지 못하면 blocked로 기록한다.
8. edu-converge로 명세·문서·코드와 검사 근거를 대조한다. 정합성·자동 검사 완료 시 ready. 사람이 화면 확인을 마치면 커밋 메시지와 파일 목록을 제공한다. 실제 커밋 후 edu-flow가 done을 확인하게 한다. 이미 실행 권한이 명시됐으면 그 범위를 따른다.

## 완료 보고

세 줄로 보고한다.
1. 무엇이 바뀌었는지.
2. 어떤 검사를 실제로 통과했는지.
3. 사람이 확인할 항목과 추천 커밋 메시지.
