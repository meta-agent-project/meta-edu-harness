# 무엇을 만들지 정하는 인터뷰

인터뷰는 앱을 미리 정해 둔 설문이 아니다. 사용자의 답변으로 만들 대상과 최초 목적을 결정한다. $ARGUMENTS에 이미 알려 준 내용이 있으면 활용한다.

1. 공통 규칙과 기존 interview·contract가 있으면 읽는다. 빈 폴더에서도 .edu/interview.md를 만들며 바로 시작할 수 있다. 환경 설정이 필요하면 이후 구현 전에 edu-start를 안내한다. 기존 문서를 빈 양식으로 덮어쓰지 않는다.
2. 알려진 답은 요약하고, 아직 모르는 중요한 것부터 한 번에 질문 하나를 한다. 우선 누가 어떤 일을 하며 무엇이 불편한지 듣는다. 비개발자에게 프레임워크 선택부터 묻지 않는다.
3. 아이디어가 없으면 방금 들은 업무와 제약에 맞는 후보 2~3개를 설명하고 고르게 한다. 예: HTML 자료 편집기, CSV 비교 도구, 견적서 생성기. 투두앱은 제안하지 않는다. 사용자가 다른 목적을 말하면 후보를 거기에 맞춘다.
4. 선택한 앱의 핵심 흐름을 입력→행동→얻는 결과로 좁힌다. 목적을 달성했다고 볼 관찰 가능한 장면, 꼭 필요한 기능, 지금 제외할 기능을 묻는다. 필요한 답이 모이면 질문을 끝내며 정해진 질문 수를 채우려고 반복하지 않는다.
5. 외부 DB 없이 메모리·로컬 파일을 사용하고, 저장이 필요하면 로컬 JSON을 검토한다. 브라우저 메모리는 새로고침 후 사라지므로 지속 저장이 필요한지 확인한다. 4시간·Pro 사용량 제약을 설명하되 충분한 토큰이나 완성 시간을 보장하지 않는다. 수업 기본은 외부 API 없음이며 제약과 충돌하는 아이디어는 대안을 함께 제안한다.
6. HTML 편집기를 선택했을 때만 .claude/edu-templates/mvp-brief.md를 읽는다. 8개 기능은 이 수업 예제의 합의 범위로 제시한다. 다른 앱에 8개 기능·특정 spec 번호·20개 레이아웃을 강요하지 않는다.
7. .claude/edu-templates/interview.md를 참고해 만들 앱·사용자·문제·완료 장면·MVP 포함/제외·보류 아이디어·미결정을 한 화면 분량으로 정리한다. 미결정은 가정이라고 표시하고 사용자에게 범위 확정을 받는다. 이미 같은 범위를 명확히 확정했다면 그 근거를 남기고 재질문하지 않는다. 미확정 상태로 구현하지 않는다.
8. 확정한 결과를 .edu/interview.md에 status=confirmed로 기록하고 contract.md와 mvp-roadmap.md에 반영한다. 기술·실행 명령은 확인된 setup/프로젝트 내용을 재사용하며 미확인 사항은 미확인으로 둔다. MVP 로드맵은 SPEC-001의 spec→목업 선택→plan→구현·검사→사람 확인→commit→첫 GitHub push다. 전체 로드맵은 MVP 사용 후 작성한다.
9. 보류 아이디어는 backlog에 중복 없이 기록한다. catalog가 없으면 생성하고 프로젝트 이름을 갱신하되 기존 features는 보존한다. .edu/bugs.md·history.md는 필요할 때 만든다. 새 프로젝트는 /edu-spec 001로 연결한다. 기존 구현의 목적을 다시 논의한 경우에는 확정된 변경을 edu-change로 연결하고 기존 spec을 몰래 덮어쓰지 않는다.
