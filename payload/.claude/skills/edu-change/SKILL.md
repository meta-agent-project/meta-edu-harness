# 요구사항 변경

1. 해당 spec·코드·검사와 요청을 비교한다. 기존 요구를 유지해야 하는 오작동이면 요구사항 변경을 멈추고 현재 개발 단계에서 재현·최소 수정·검사로 처리한다. 기대가 모호할 때만 짧게 확인한다.
2. 변경 전후·유지할 동작·영향받는 기능을 요약한다. 같은 spec ID와 파일에서 요구와 필요한 AC만 최신화한다. 연결 spec은 실제 영향이 있는 경우만 수정한다.
3. 변경 이유와 검사 변경 근거를 현재 plan의 변경 사유에 짧게 적는다. 별도 history.md나 일반 변경용 ADR을 생성하지 않는다. 이전 내용은 Git diff/log로 확인한다.
4. 해당 상태를 specified로 되돌리고 기존 validation을 이전 버전 근거로 표시한다. 화면 변화가 있으면 부분 목업을 선택하고, 없으면 생략 근거를 남겨 edu-plan으로 연결한다.
5. 다음은 plan → 실패 테스트 → 구현 → 통과 → 누적 회귀 검사 → edu-converge → 사람 확인·커밋이다. 여기서 명세를 고치기도 전에 코드를 수정하지 않는다.
6. 커밋 메시지에 spec ID, 무엇을 왜 바꿨는지, 갱신한 검사 이유를 담는다. 유효한 기존 검사는 유지한다. 커밋되지 않은 변경을 Git에 보존됐다고 설명하지 않는다.

사용자가 구현까지 요청했고 범위가 확정됐다면 필요한 스킬의 절차를 읽어 위 흐름을 순차로 끝낸다. 명세 수정만 요청했다면 그 범위에서 멈춘다. 이미 확정한 변경·선택·실행 권한을 반복해서 묻지 않는다.
