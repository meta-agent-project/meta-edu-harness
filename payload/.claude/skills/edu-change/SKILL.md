# 요구사항 변경

1. 요청에 해당하는 기존 spec·현재 코드·검사 결과를 읽는다. 실제 동작이 spec과 다른 버그이고 기존 기대를 유지해야 한다면 문서·코드를 바꾸지 않고 edu-fix로 연결한다. 이 스킬은 기대 동작 자체의 변경만 다룬다. 모호한 기대는 짧게 확인한다.
2. 무엇이 바뀌고 무엇을 유지할지, 영향받는 spec·화면·검사를 짧게 보여준다. 변경 의도가 이미 명확히 확정됐으면 반복해서 확인하지 않는다. 충돌·모호함만 질문한다.
3. 요구사항 변경이면 같은 spec 파일을 최신화한다. 안정된 spec ID와 AC를 유지하고 필요한 AC만 추가·갱신한다. 연결된 다른 spec은 실제 영향이 있을 때만 고친다.
4. history.md에 날짜·spec ID·변경 전·변경 후·이유·영향 범위·검사 갱신 이유를 추가한다. 코드 구현이 아직이면 구현 예정으로 표시하고 완료를 미리 쓰지 않는다.
5. 중요한 구조 결정이 생겼을 때만 별도 ADR에 선택·대안·이유를 적는다. 일반 기능 수치 변경은 history로 충분하다.
6. 변경한 spec의 상태를 specified로 되돌리고 이전 검사 결과가 이전 버전의 기록임을 표시한다. 화면이 달라지면 부분 mockup→plan, 화면이 같으면 생략 사유 기록→plan으로 이어간다. 여기서 코드를 바로 수정하지 않는다.
7. 구현 후 validation·history의 완료 상태를 갱신하도록 다음 단계를 안내한다.
