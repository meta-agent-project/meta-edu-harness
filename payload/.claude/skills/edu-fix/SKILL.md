# 명세대로 돌아오게 하는 버그 수정

대상은 $ARGUMENTS의 증상·BUG ID·spec이다. 기능을 새로 설계하는 edu-change와 구분한다.

1. 공통 규칙, 해당 spec의 AC, 관련 코드·검사·최근 변경만 읽는다. 기대 동작이 명세와 일치하는지 확인한다. 새 기능이나 기대 동작 변경이면 edu-change로, 나중에 할 아이디어면 edu-flow backlog로 연결한다. 명세가 없거나 모호하면 기대 결과 하나를 확인하고 근거를 기록한다. 버그를 맞는 동작으로 보이게 spec을 바꾸지 않는다.
2. 재현에 빠진 정보만 짧게 묻는다: 어떤 입력에서 어떤 순서로 했는지, 기대 결과와 실제 결과는 무엇인지. 기존 로그·파일·답변을 다시 요구하지 않는다. 민감한 원본 대신 최소 샘플을 사용한다.
3. .claude/edu-templates/bug-report.md를 참고해 .edu/bugs.md에 BUG ID·연결 spec/AC·재현 순서·기대/실제를 기록한다. 같은 버그면 기존 항목에 이어 쓴다. 직접 재현한 사실과 사용자 보고를 구분한다. 재현하지 못하면 재현 안 됨/추가 정보 필요로 남기고 추측으로 코드를 고치거나 해결됐다고 쓰지 않는다. 실행 환경 문제는 차단 사유로 구분한다.
4. 재현됐다면 원인 가설과 최소 수정 계획을 bugs.md에 짧게 적는다. 해당 동작만 검사하는 회귀 테스트를 먼저 추가하거나 이미 실패하는 유효한 테스트를 재사용한다. 수정 전 실제 실행으로 증상 때문에 실패함을 확인한다. 구문·경로·설치 오류를 해당 버그의 회귀 테스트 실패로 대신하지 않는다.
5. 자동화하기 어려운 화면 문제는 재현 조작·수정 전후 수동 확인을 계획하고 자동 테스트 미작성 이유를 남긴다. 도구가 없으면 사람의 확인을 요청한다. 수동 확인을 자동 TDD라고 부르지 않는다.
6. 관련 기능은 building으로 표시하고 기존 validation은 과거 결과로 보존한다. 현재 작업·다른 사람의 변경을 덮어쓰지 않고 원인을 고치는 최소 수정만 한다. 무관한 리팩터링·추가 기능·새 시안은 만들지 않는다. 같은 실패를 두 번 수정해도 해결되지 않으면 blocked와 원인·시도·다음 확인을 남겨 강사에게 넘긴다.
7. 해당 회귀 테스트와 영향을 받는 기존 검사를 실행한다. 마무리 때 누적된 빠른 검사(starter는 npm test)를 한 번 실행한다. 실제로 영향을 받는 사용자 흐름도 확인한다. 매 수정마다 전체 통합 검사를 돌리지 않으며, 실패를 감추려고 유효한 테스트를 삭제하거나 약하게 바꾸지 않는다.
8. bugs.md와 연결 spec의 validation.md에 원인·수정 파일·수정 전 실패/수정 후 결과·실제 실행 명령·남은 확인을 적는다. 변경 없는 spec 요구사항과 history는 유지한다. 새로 보호한 조건을 기록하되 모든 회귀 방지를 보장하지 않는다.
9. 실행 가능한 검사 통과 뒤에는 ready/사람 확인 대기로 둔다. 미실행 항목을 명시하고 사람이 확인한 뒤 추천 commit 메시지(fix: BUG-001 …)와 변경 파일을 보여준다. 실제 확인과 커밋이 끝나면 버그를 해결로 기록한다. 전체 spec이 다른 이유로 미완료면 done으로 바꾸지 않는다. catalog는 실제 상태로 갱신한다.

완료 보고: 원인 / 수정한 내용 / 실제 검사 결과와 남은 확인. 자동 commit·push는 공통 Git 규칙을 따른다.
