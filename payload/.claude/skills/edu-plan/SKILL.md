# 구현 계획

1. 현재 spec·선택된 목업·mockups/design-choice.md·직접 관련된 코드와 테스트를 읽는다. 디자인 기록이 없던 기존 프로젝트는 확인된 선택 이유를 재사용한다. 초기 프로젝트이면 실제 존재하는 파일부터 확인한다.
2. .claude/edu-templates/plan.md를 참고해 .edu/specs/번호/plan.md를 쓴다. 작업별 결과·변경 파일·연결 AC·검사 방법을 적는다. 없는 파일은 새 파일이라고 표시한다.
3. 기술 후보를 매번 재조사하지 않는다. contract의 검증된 기본 기술을 사용하고 추가 도구가 필요한 이유만 설명한다.
4. 자동 검사와 사람이 확인할 흐름을 구분한다. MVP는 합의한 핵심 흐름과 데이터 보존을 우선한다. HTML 편집기 예제는 선택 대상만 변경·이동과 삭제 격리·내보내기 보존을 검사한다. 순수 상태 함수의 테스트만으로 실제 브라우저 흐름을 검증했다고 하지 않는다.
5. 대표 TDD 기능은 새 실패 검사를 먼저 쓰는 순서, 유지할 기존 검사, 변경된 요구사항 때문에 갱신할 검사를 적는다.
6. 기능 완료 때 빠른 누적 테스트와 영향받는 사용자 흐름, edu-converge를 확인하는 순서를 포함한다.
7. status=planned로 기록하고 5줄 이내로 요약한다. 다음은 edu-build다. 자동으로 여러 기능을 이어 구현하지 않는다.
